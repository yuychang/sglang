The ask

Investigate and optimize Kimi‑K3 on ROCm with multi‑stream enabled

What "multi-stream" means here

K3 already has a 3-slot pool of CUDA streams (self.alt_streams) used to run small, independent GEMMs on a side stream concurrently with the main compute stream — hiding their latency instead of paying it serially.

What we found first

On HIP, that pool is unconditionally None. Every overlap site in the model silently degrades to fully serial execution. This is a single line, but it disables three separate optimizations at once.

Follow-up ask

"Refer to github.com/ROCm/ATOM and see how it implements multi-stream Kimi‑K3 — we can leverage their experience." → ATOM's public design notes point at a token-count threshold (not GPU-family gating) and a specific MI355X crossover point, which became the gating strategy we adopted.

Why this shape matters for overlap

MoE's shared expert is a fixed, small amount of work regardless of routing. Routed-expert work is the long pole. If shared-expert compute can run on a side stream while routed-expert compute proceeds on the main stream, the shared expert's latency is hidden almost for free.

Same idea, twice more

KDA's forget-gate projection and MLA's output-gate GEMM are both small, data-independent side computations relative to their layer's main GEMM — same overlap shape, different slot in the pool.

3 / 16Finding #1
Finding #2 (the deeper one)

Even with the pool restored, MoE overlap still wasn't reachable

The only dual-stream fork in KimiK3MoE._forward_fused was gated on k3_ar_fusion.enabled() — a Blackwell (SM100/SM103) fused all-reduce feature. That gate is False everywhere else.

AR-fusion path

Dual-stream MoE already existed here: shared + routed forked, joined, then a fused multicast all-reduce. Only reachable on Blackwell.

Plain-TP path (everyone else)

Serial: shared expert runs to completion, then routed expert runs, then one plain collective. This is the path ROCm and H100/H200 take.

Consequence: restoring the stream pool alone would have changed nothing observable on ROCm — slot [0] would still never be entered. The pool and the MoE fork are two independent gaps that both needed closing.

4 / 16Finding #2
Prior art

What we took from ROCm/ATOM

Gate on tokens, not on GPU family or capture mode

ATOM's dual-stream MoE is controlled by ATOM_DUAL_STREAM_MOE_TOKEN_THRESHOLD — overlap is only worth forking a stream for once there is enough routed-expert work to hide the shared-expert latency behind. Below that, the fork/join overhead isn't worth it.

Measured crossover, not a guess

ATOM's default threshold reflects a value measured on MI355X for this exact shared-vs-routed split. We reused that number (1024 tokens) as our default rather than inventing a new one.

What we adapted rather than copied

  • ATOM's environment targets its own runtime; we mirrored the idea (env-gated token ceiling) as a native SGLang EnvInt, not a port of their code.
  • SGLang's stream pool has 3 conceptual slots vs. ATOM's single MoE stream — we had to decide how those fold onto HIP's limited hardware queues (next slide).
  • We kept SGLang's existing capture-mode guards (is_in_breakable_cuda_graph, is_in_tc_piecewise_cuda_graph) in addition to the token ceiling, since ATOM and SGLang don't share a graph-capture design.
5 / 16ATOM reference
ROCm-specific constraint

Why HIP streams can't just mirror CUDA 1-for-1

The rule

HIP does not give each stream its own hardware queue. Streams are round-robined across GPU_MAX_HW_QUEUES (default 4). If two streams that need to run concurrently land on the same queue, the runtime serializes them — you pay the fork/join overhead and get zero overlap benefit.

Our response

  • Module constant _HIP_MIN_HW_QUEUES = 5, documented in code.
  • Fold slots [0] and [1] onto one physical stream (they never run concurrently in K3 — [1] is unused dead weight inherited from the MLA base class), keep [2] separate.
  • Warn at construction time if GPU_MAX_HW_QUEUES < 5.
  • Document GPU_MAX_HW_QUEUES=5 in the AMD cookbook recipe.

_build_alt_streams(): opt-in, folded pool

def _build_alt_streams():
    if not _is_hip:
        return [torch.cuda.Stream() for _ in range(3)]

    if not envs.SGLANG_ROCM_USE_MULTI_STREAM.get():
        return None  # opt-in: unchanged default behavior

    hw_queues = _get_hip_hw_queue_count()
    if hw_queues < _HIP_MIN_HW_QUEUES:
        logger.warning(
            "SGLANG_ROCM_USE_MULTI_STREAM=1 but GPU_MAX_HW_QUEUES=%d "
            "(< %d) — streams may collide onto the same HW queue "
            "and serialize. Set GPU_MAX_HW_QUEUES=%d or higher.",
            hw_queues, _HIP_MIN_HW_QUEUES, _HIP_MIN_HW_QUEUES,
        )

    moe_and_mla = torch.cuda.Stream()      # slots [0] + [1]
    kda_bfa_or_mla_gate = torch.cuda.Stream()  # slot [2]
    return [moe_and_mla, moe_and_mla, kda_bfa_or_mla_gate]

CUDA unchanged: 3 distinct streams.

HIP, default unchanged: None. Zero risk to existing deployments.

HIP, opt-in 2 physical streams, folded per slide 4/7's analysis, with a startup warning if queues are short.

Implementation · fix #2

Giving the plain-TP MoE tail somewhere to fork

def _dual_stream_single_collective(self, num_tokens):
    return (
        self.alt_stream is not None
        and not k3_ar_fusion.enabled()
        and 0 < num_tokens
            <= envs.SGLANG_K3_DUAL_STREAM_MOE_MAX_TOKENS.get()
        and not is_in_breakable_cuda_graph()
        and not is_in_tc_piecewise_cuda_graph()
    )

Five conditions, all must hold

  • Pool exists — CUDA always; HIP only when opted in.
  • Not already the AR-fusion path — avoid double-forking; that path has its own dual-stream logic.
  • Token ceiling (default 1024, ATOM's measured MI355X crossover) — below this, fork/join overhead isn't worth it. 0 is a hard kill switch.
  • Not in a breakable / TC-piecewise capture — multi-stream forking is unsafe when the graph can be split mid-region.

Implementation · the diff

The fork, in _forward_fused

if self._dual_stream_single_collective(num_tokens):
    current_stream = torch.cuda.current_stream()
    self.alt_stream.wait_stream(current_stream)   # order vs. what's already queued

    self._forward_routed(hidden_states, router_logits, routed_input, latent)  # main — issue first, it's longer
    with torch.cuda.stream(self.alt_stream):
        self._forward_shared(gate_up, shared_output)               # alt — writes a disjoint buffer slice

    current_stream.wait_stream(self.alt_stream)              # join before the single collective
else:
    self._forward_shared(gate_up, shared_output)                   # original serial path, byte-for-byte
    self._forward_routed(hidden_states, router_logits, routed_input, latent)
Why routed first?

It's the longer op; issuing it first on the main stream maximizes the window the alt stream has to hide the shared expert behind it.

Why is this safe?

Shared and routed write to disjoint slices of the output buffer — no data race, no accumulation order dependency.

What's untouched?

The single collective after the join is completely unmodified — same call, same buffer, same place in program order.

10 / 16The diff
Correctness

Bit-identical, not "close enough"

Why we can claim exact equality

  • Same two function calls, same inputs, same arithmetic — only the stream they're issued on changes.
  • Disjoint output buffer slices → no write-write hazard, no floating-point reduction-order sensitivity between the two ops.
  • wait_stream pairs enforce the same effective ordering constraints a single stream would have given for free.
  • The reduction/collective that combines them is untouched.

How we verified it

Test asserts torch.equal(fork_output, serial_output) — zero tolerance, not torch.allclose. Run at 1, 4, and 32 tokens, and again through actual CUDA graph capture + replay to catch anything the eager path might miss.

13 / 16Summary
Scope

Who else does this affect?

AMD / ROCm

The headline target. Opt-in via SGLANG_ROCM_USE_MULTI_STREAM=1 + GPU_MAX_HW_QUEUES≥5. Default behavior (env unset) is unchanged — zero risk to existing ROCm deployments that don't opt in.

H100 / H200 (and any non-AR-fusion CUDA GPU)

These GPUs already had alt_streams, but were also hitting the serial plain-TP MoE tail, since k3_ar_fusion is Blackwell-only. The new fork benefits them automatically — no opt-in needed, since the pool already existed there.

Framed differently: this wasn't only a ROCm bug. ROCm made the gap fully visible (pool and fork both missing), but the MoE-tail fork was a latent gap for every non-Blackwell CUDA GPU running K3 in plain-TP mode too.
